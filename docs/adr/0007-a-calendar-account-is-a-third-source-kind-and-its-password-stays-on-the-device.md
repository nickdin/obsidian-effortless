# 0007 — A calendar account is a third kind of source, and its password stays on the device

- **Status**: accepted
- **Date**: 2026-10-21
- **Deciders**: the author
- **Ticket**: #1212, built by #1213 and #1214, recorded by #1215

## Context

[ADR 0001](0001-ics-is-the-only-calendar-format.md) made a *calendar source* either a published `.ics` link or an `.ics` file in the vault. A link is one plain request with no sign-in, so a calendar the plugin can read is a calendar anyone holding its address can read.

The author switched off public sharing for three iCloud calendars, no longer wanting them public, and reported on 2026-10-20 that every link Effortless held for them had answered 404 since 2026-10-18 21:09. Nothing in the plugin could sign in anywhere, so a private calendar was one it could not see at all. The only way back was to make the calendars public again.

## Decision

**A calendar account is a sign-in to a calendar server that speaks CalDAV**, the protocol desktop calendar apps use: the server's address, a user name, and an **app-specific password** — one the provider issues for a single application, so the person's own password is never typed into the plugin. *Fetch calendars* signs in and lists the calendars the account holds. **Each calendar the person ticks becomes a source row of a third kind, `account`**, beside `link` and `file`, with the two switches, the read state and the per-source gate of #1211 every other source has. Each refresh reads each such calendar with one `REPORT` request over a fixed span (GLOSSARY **Calendar account**). The server answers with each meeting's `.ics` text inside its XML. The plugin unwraps it into one calendar and hands that to the reader the links use.

Three choices inside that, each settled by the author on 2026-10-20 in #1212's triage. The reason given for each is #1212's; a sentence marked *Added when recorded* is this ADR's own reasoning, not part of the decision.

- **Why a kind of its own.** An account is a new thing, and each calendar the person picks on it becomes its own source row, because one account can carry several calendars while one source is one calendar. *Added when recorded*: the person does not know those calendars' addresses, since they are found by signing in rather than pasted, which is why a link that carries a password would not do. Making each calendar its own source row keeps everything already built per source — the two switches, the read state, the gate that stops a source that did not read whole from removing anything — unchanged, and nothing downstream learns the source's kind.
- **Why the password stays on the device rather than in `data.json`.** `data.json` sits inside the vault, so Obsidian Sync carries it onto every device and every backup carries it too. A password written there travels wherever the vault does. The password is kept instead in Obsidian's keychain, `app.secretStorage`, under the id `effortless-calendar-<account id>`, and never synced. The keychain is not a vault file, so Obsidian Sync never carries it; on a desktop it is encrypted with the operating system's key store where one runs and kept as plain text where none does, and on a phone it is the system's secure storage (#1217, read from Obsidian 1.14.4's own code). Until #1216 it sat in the plugin's per-device store, Obsidian's local storage for this vault on this device; a password found there is moved into the keychain when the plugin starts, and leaves the old place only once the keychain reads it back. The price is that it is typed once on each device that should read the account; a device without one shows *This device has no password for this account* and asks nothing of the server. The server address and the user name are not secrets and travel with the vault in `data.json`, so the account appears on every device and only the password has to be typed. If the password leaks, revoking it at the provider is the remedy, and that works whichever device held it.
- **Why any CalDAV server, rather than iCloud alone.** Other providers speak the same protocol with the same sign-in as iCloud, so tying the kind to Apple would cost the code nothing less. *Added when recorded*: it would also leave someone with another provider unable to use it. iCloud's address, `https://caldav.icloud.com`, is filled in when an account is added; any other address can be typed over it.

**This amends 0001's "a source is a link or a file"**: a source is a link, a file, or one calendar of a calendar account. The rest of 0001 holds unchanged — `.ics` is still the only calendar format the plugin reads, and an account's calendar arrives as `.ics` text.

## Alternatives considered

- **Make the calendars public again.** The workaround while this was built. Rejected as the answer because a private calendar is exactly what the author asked to keep.
- **Keep the password in `data.json`.** Typed once for every device. Rejected because it then travels into every device and every backup of the vault. *Added when recorded*: an iCloud app-specific password signs in to the whole account, which lets an app reach the person's mail and contacts as well as their calendars ([Apple](https://support.apple.com/en-us/102654)). That makes it a larger key than any published link the vault already holds.
- **iCloud only.** No simpler to build, for the reason above, and it would make the kind's name a promise about one provider.
- **Sign-in through the provider's own consent screen (OAuth).** Needs a registered application and a consent screen per provider. Out of scope in #1212.

## Consequences

- **A calendar the person keeps private can be read**, and a secret the plugin never had before now sits on each device that reads the account. The settings box for it is masked, the plugin's own box rather than Obsidian's secret picker, and once a password is typed its description says it is kept in Obsidian's keychain on this device only. It does not claim encryption, which the keychain gives only where the operating system has a key store.
- **The first request in the plugin that carries a sign-in.** An address that does not start with `https://` is refused before the password is sent, so the password never travels unencrypted. The one exception is a server on the same computer, which may use `http://`.
- **Each device asks for the password once.** A phone and a desktop each need it typed, and a device without it reads none of the account's calendars and says so on each of their rows.
- **A refused password and a calendar gone from the account are failures of their own**, each said on the source's row in words that name the password or the missing calendar rather than the address. Like a dead link, neither removes anything from any day.
- **Obsidian's keychain holds the password, and the plugin needs Obsidian 1.11.4.** Found as an open question when this was recorded, and answered by the author on 2026-10-21: a secret there stays on the device, as decision 1 requires, and is encrypted where the operating system can. `app.secretStorage` (`node_modules/obsidian/obsidian.d.ts:458`, its class at `:5635`) is published since 1.11.4, so `minAppVersion` rose from 1.8.7 to 1.11.4 with plugin version 0.0.2, and `versions.json` keeps an older Obsidian on 0.0.1. The keychain publishes no way to delete a secret, so a forgotten password is an empty one, and every reader takes empty for none.
- **A meeting outside the fixed span is not seen**, even one a repeat rule would put there. The span reaches past every window that reads it, so no setting could make it too short (GLOSSARY **Calendar account**).
- **What a refresh costs, measured** on 2026-10-21 on build `8dd1b2e` in the test Obsidian, against a Radicale 3.8.3 server on the same machine, counting HTTP bytes on the wire before TLS. One refresh of one account with three calendars was **3 requests**, one per calendar, with no sign-in step and no discovery. Those run only when *Fetch calendars* is pressed. The three calendars empty cost **3,383 bytes**; holding 57 meetings with varied text they cost **16,444 bytes**. The server compresses its answer, which is why the second figure is small. That is about 1.1 KB per calendar plus about 230 bytes per meeting in the span. At the fifteen-minute cadence that account costs about 1.6 MB a day before TLS. The phone was not measured, and neither were TLS or a real iCloud answer (`docs/acceptance-shots/issue-1215-refresh-cost.txt`). The cadence stays at fifteen minutes on every device; changing it is a later ticket's, with these numbers.
