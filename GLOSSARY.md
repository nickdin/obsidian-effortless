# Effortless

An Obsidian plugin that keeps tasks and days in plain notes, taking over the copying between pages and leaving every decision about a task to the person. This file is the glossary: what each word means here, and which near-synonyms not to reach for. **This governs the code's own identifiers as well as its prose**, but `manifest.test.ts`'s sweep checks documents, the strings the plugin shows a person and its default settings, never an identifier — so a green suite is not a guarantee there, and an identifier still drifting from this glossary is left to review.

## Language

**The day's log**:
One note per calendar day, holding what was planned for that day and what happened in it. The plugin's central place. It is a **mirror and holds no state of its own**: everything in it is explained by what some collection says, so the plugin never has to remember anything about a day that is not written in a file.
_Avoid_: daily note, journal

**The day's-log template**:
The note `layout.dailyLogTemplate` names, blank until answered. Answered, `createDailyLog` (`src/core/noteWriter.ts`) builds a new day's log from that note's own text — its own section order and its own frontmatter kept as written — instead of `dailyLogFrame`'s generic, built-in one (`src/core/vaultLayout.ts`); blank leaves the built-in frame untouched. Its `{{date:FORMAT}}`, `{{yesterday:FORMAT}}` and `{{tomorrow:FORMAT}}` placeholders are filled for the day being created, in the syntax Obsidian's own core Templates plugin uses on purpose, so a template written for it reads the same here. A heading the built-in frame would write that the template leaves out is added the way a missing section always is; one it already carries is never duplicated. Built by `src/core/dailyLogTemplate.ts`.

**Collection**:
A note gathering everything about one subject, where a task lives once it has been decided on. **A note is a collection when it carries the configured tasks heading, and for no other reason** — not its folder, not its tags (issue #29, ADR 0003). The day's log is never one. The bullet journal method's own word, taken deliberately on the author's call (2026-09-04, issue #27) over the earlier *project file*. It is imprecise — in the method a *collection* is the general category, and the day's log is itself one — and the imprecision is accepted, because this is the word the person who reads this vault uses.
_Avoid_: project, project file, area, topic note, workspace

**The tasks heading**:
The one heading, named once for the whole vault, that marks a note as a collection and bounds what the plugin reads inside it. Matched on its whole line, ignoring capitals and ignoring the heading's level, so different collections may use different heading sizes. A checkbox anywhere else in the note is invisible to the plugin. It is **not a *section***: it carries no level, and a section is one of the levelled headings a new day's log is framed from. The two names retired below are retired for *this* heading; **the day's task sections** are a different thing, in the day's log rather than in a collection.
_Avoid_: task section, tasks section, required tag, root folder

**The completed-tasks heading**:
The heading, named once for the whole vault, that a collection's finished tasks are moved under. It lives inside a collection, not in the day's log, and it is the one of the two the plugin writes rather than only matches. Like the tasks heading it carries no level and is **not a *section***.
_Avoid_: done section, completed section, archive

**The day's task sections**:
The levelled sections of the day's log that hold task lines — the one a rolled-over task reappears under, and any other a feature asks for. Each is a *section*, so each carries its own heading text and its own level. None of them is the **tasks heading** or the **completed-tasks heading**: those two carry no level and live in a collection, never in the day's log. **Two of them are in `VaultLayout` now: `todayHeading` and `overdueHeading`**, shipped with the English defaults `Today` and `Overdue`, overdue directly above today (issue #801, decision 5 on issue #709). Spec issue #32 reserves the group — one heading entry per named section: the notes heading in the day's log, the calendar heading, and the day's task sections — and keeps that group "open to the feature tickets and closed to the features themselves". #801 is that group's first addition: the feature ticket that needed the two headings added them to the group, rather than carrying a heading of its own, exactly as this entry has always said. *task section* and *tasks section* are retired under **the tasks heading**, where the whole point is that a heading carrying no level is not a section. These are the opposite case: every one of them *is* a section, and this is spec issue #32's own term for the group. Renaming it here alone would put the glossary and the spec out of step, which is what issue #182 was built to avoid. So the retirement stands for that heading and this name is a deliberate exception to it, said here so that the reader of this entry meets it and not only the reader of the other one.

**Pairing**:
The link between a task's line in a collection and its copy in a day's log, held in a hidden marker inside both lines rather than in either note's name or place. A pairing **breaks** when the collection stops being one — its heading renamed, the note deleted or moved out of reach — and the plugin then keeps both files untouched and says so, once per event. It **heals** on its own the moment the collection matches again. **Task consistency** is the feature that keeps it; the run that keeps every pairing in step is issue #810, and the pairing's first copy is issue #807. **The marker's own hash sees only what travels between the two copies — decision 8's five fields, the checkbox by meaning with `copied` and `forwarded` masked to the meaning they annotate — and nothing else.** Decision 7 named the description as a sixth, hashed field; decision 8's own closing paragraph says words are never compared and never copied, and that is the sentence the hash now follows, because a hash sensitive to a word edit, a hand-typed `[>]`, or a fresh copy's own `/` reports a change this feature will never act on — which is what left a freshly copied pair un-copying itself on its first reconcile, and left a same-side word edit blocking the other side's real field edits forever.
_Avoid_: link, sync, binding

**Migration**:
The feature, registered under the id `migration` and shown as *Migration*. Moving a task into the collection it belongs to, and marking the original `[>]` in the note it was written in. **It starts from the notes heading of the day's log, or from any note that is not a collection**, under any heading, outside fenced text and frontmatter and outside an excluded folder; a collection is refused. **Not** the bullet journal method's own sense of the word, which is a move from one time period to another — day to day, day to month. Three published Obsidian plugins do the method's kind; none does this kind, and confusing the two loses the distinction the plugin exists on (issue #25, `docs/research/bullet-journal-niche.md`). Both kinds of move are nevertheless written `[>]` — see *Forwarding*. **Always the person's act**, on one task line or a selection of them, by the command, the right-click entry or a hotkey the person sets — the command ships with none — and only for a task in one of those two places with one of the five symbols the plugin understands, never a note, an idea or a plain bullet; nothing is ever put in a collection unasked, and it adds no date, because *when* is a decision. **The collection gets the task's own line and the note it came from keeps a frozen one**, both carrying the hidden comment `%% migration:<id> <hash> <box> L %%` (the box the task had, and `L` for the link the plugin added; older filings carry fewer words); that line also names the collection with an ordinary `[[…]]` link. **It is reversible while the collection's line is untouched** — not reworded, not ticked — and the person can go from the frozen line to the task. **It does not collide with Task consistency and can look as if it does**: a task filed with a date of today or earlier is copied into today's log by Task consistency's next run, so, for a task that came from the day's log, the same day can show the frozen `[>]` line and a live copy — correct, and it reads as a duplicate the first time. The word is not on *Roll-over*'s `_Avoid_` line because this feature carries it as its name; the two are told apart by these two entries, not by the sweep. The plugin's seventh feature, and like every other it may never reference one.
_Avoid_: carry-over, rollover, moving forward, filing

**Forwarding**:
What `[>]` on a line means: this line is no longer the live one, look elsewhere. It covers **two different moves**, and the heading the line sits under is what tells them apart to a reader — under the notes heading (`# Anteckningar` in the vault it was written for) the task went into a collection (*Migration*), under one of *the day's task sections* it went to the next day (*Roll-over*). **In a note that is neither a day's log nor a collection, a `[>]` line carrying Migration's marker always means the task went into a collection**, because roll-over never writes outside the day's log. One mark for both is the author's call (2026-09-04, issue #27). **What the code acts on is narrower than what a reader sees.** Migration acts on a `[>]` only when it carries Migration's own `%% migration:<id> <hash> %%` comment and sits in a day's log outside a fenced block, or in any other note that is not a collection and not in an excluded folder, outside fenced text and frontmatter — the jump command and the two right-click entries that act on a frozen line (*Go to this task in its collection* and *Undo migration*) ask that one check (`frozenLineAt`, for the line pressed; the filing entry asks `filableCheck` instead, in a day's log as in every other note, and the notice's undo button undoes by id), so a `[>]` typed by hand is a task Migration will put in a collection but never one it jumps from or undoes. Task consistency's own `[>]` carries Task consistency's comment and is never read as Migration's, nor the reverse: each feature reads only its own. Only the first of the two headings existed until issue #801: the roll-over side is `overdueHeading` now, and no code reads the heading itself to tell the two moves apart — the comment does — so the rule that the heading is the disambiguator holds for a person reading the log, and for code only through the comment. A forwarded line is **frozen**: the plugin never rewrites its words again, keeping only the collection's name on it current — the one edit a frozen line ever receives, and the plugin's own rather than Obsidian's — because a day's page records what was written that day. **That last edit is the core's, not one feature's.** The link on a line Migration froze is an ordinary `[[…]]` link, and `src/core/collectionRename.ts` rewrites it when the collection is renamed without naming Migration; undo and the jump read the link as it stands and, for undo, try the collections of that name as well. **The mirror is kept the same way**: the link back on a collection's copy, to the note the task was filed from, is rewritten by the same core module when that note is renamed, found through the marker's own flag (`appendedLink`) rather than by naming Migration, so a person's own link to the same note is never touched; a rename of a note no collection links to reads no note. *Driven*: `docs/acceptance-shots/issue-864-drive-5-rename.txt` steps 8 and 8b renamed a collection with Obsidian's own link-updating setting on and off (`getConfig("alwaysUpdateLinks")` read back each time), and with it off the plugin's core rewrote the frozen lines once the day's log was no longer the note on screen, so the rewrite is the plugin's and does not depend on Obsidian's setting.
_Avoid_: moved, deferred

**Roll-over**:
A task planned for a day and not done reappearing in the next day's log, under the overdue heading. The day it left keeps its line, marked `[>]`, so a page still records what was planned and that it did not hold. The bullet journal method's own sense of *migration*, which this repository does not call migration. Built by issue #809, which also freezes the old day's line, and driven by the run of issue #810.
_Avoid_: carry-over, rollover as one word

**Clash**:
Two copies of one task, both changed since the plugin last saw them, disagreeing. The plugin **keeps both and changes neither**, and says so — it never picks a winner, because picking one is deciding. Distinct from an ordinary edit, where only one side moved and the other simply follows. **Task consistency** is the feature that finds it and reports it. **Reported through `host.problems`, never written into either file** — one `Notice` naming the task the first time, and one settings-screen line carrying the words as they read on each side, kept until the lines next agree. ADR 0002's own words, "writes one line in the log naming the task," are superseded by spec #32's standing-problem channel, which makes writing anything into a note through it structurally impossible.
_Avoid_: conflict, merge conflict

**Copying**:
Writing the same task out a second time by hand. What the plugin takes over. Distinct from *deciding*, which it never takes over. **Task consistency** is the feature that does it. Its first copy of a task, from a collection into the day's log, is issue #807; a task's words are never copied, only the five fields that travel.

**Marker**:
The hidden comment `%% task-consistency:<eid> <hash> %%` that ends a task's line in both the collection and the day's log, and is what makes the two lines a **pairing**. The `eid` is the pairing's own id, made once when a task is first copied and kept when a deleted log line comes back; the `hash` is what the five travelling fields read as when the plugin last copied them, so that a change since then can be told from none. It is a hidden comment, not a *symbol*: **Symbol** retires *marker* as a name for the character inside a checkbox, because the word is already spent — on the list marker (`-`, `*` or `1.`) that opens a task line, and on this comment. **Migration** writes a marker of its own, `%% migration:<id> <hash> %%`, on the line it files and on the frozen line it leaves; each feature reads only its own. It is added, replaced and removed through the core's one comment-editing function, never by rebuilding the line, and it is written at the same point on the line every added field goes. A line that carries none is never a pairing, however much it looks like one: a task typed into the log with a collection's name on it and no marker is left exactly as typed.
_Avoid_: id comment

**Context bullet**:
The one plain line, with no checkbox, that stands in the day's log for a parent task that is not due when one of its subtasks is. It carries the parent's own words and dates, and the due subtasks come in under it; three due subtasks of one parent share one bullet. It is not a task, so it is never paired and never ticked.
_Avoid_: header task

**Deciding**:
Choosing where a task goes next, or whether it is still worth doing. Always the person's, one task at a time. The rule for whether a feature belongs here is that it removes copying without removing a decision.

**Feature**:
An Obsidian `Component` the core loads and unloads on demand, declaring an id, a name, a one-line description, its own settings and a readiness check — and nothing else. A feature may never reference another feature.
_Avoid_: module, plugin, extension

**Task consistency**:
The feature, registered under the id `task-consistency` and shown as *Task consistency*. Keeps a task's line the same in its collection and in the day's log, editing one field at a time rather than rebuilding the line — the feature that keeps a **pairing**, resolves a **clash** and does the plugin's **copying** for a task. It stores nothing of its own in `data.json`; its only state is the pairing marker inside the files it edits (ADR 0002). It is **not configured** until the daily-log folder and filename are both answered; a blank tasks heading is not a reason it cannot run, because a person with a day's log and no collections yet has nothing to copy. It **never runs on a phone**, whatever the settings say — the one reason left standing once its own conflict handling and its atomic writes disposed of the old plugin's other two defects (spec issue #709 decision 14, § *Off phones*). **Runs per file, not on a whole-vault rescan**: a relevant file changing — the day's log, or a note the collections index calls one — schedules a debounced check of that file alone a couple of seconds later, and a sweep ten seconds after the plugin starts and every fifteen minutes after catches a task crossing into due purely because midnight passed, with no file touched at all. The plugin's sixth feature, and like every other it may never reference one.

**Feature state**:
The one thing a feature's row on the settings screen says about it, and the only place the seven answers are combined. Seven members, decided by a fixed precedence — *failed*, *not available here*, *off*, *standby*, *not configured*, *not started*, *running* — so exactly one badge is ever true at a time. *Standby* and *not started* keep the *off* badge on purpose: the row's sentence, not a badge of its own, is what says another device does the job or that this one never started it. A feature is *not started* when it is switched on and ready and yet was never attached — a load it refused, or a registration after the plugin started. A feature on *standby* is constructed but not loaded, like one this device cannot run at all: it stood itself down, so nothing of it runs here until its readiness is asked again. **Only the *Build the days on this device* switch asks today** — a feature standing itself down for any other per-device reason stays down until the plugin reloads. Read from `readiness()` plus the stored switch on every screen draw, and **never written to `data.json`** — availability is this device's answer and that file syncs.
_Avoid_: status, mode, enabled

**The core**:
Everything two features must agree on: the task-line format, the vault layout, the calendar sources, the single `data.json`, the note-writing queue and the settings screen. The only writer of `data.json`.

**Fenced block**:
A run of three or more backticks or three or more tildes opens one; a run of the same character, at least as long, followed by nothing or by any run of spaces and tabs, closes it — CommonMark's rule, read by `openingFence` and `closesFence` in `src/core/markdownSections.ts`. **That closing rule is narrower than the calendar reader's own copy, kept until issue #412 moved the fence rules into the core**: the private copy closed on any whitespace, the core's closes only on a space or a tab, and the narrowing was kept on purpose (ADR 0004, issue #505) — CommonMark is this module's own stated contract, and Obsidian's renderer was measured to agree. A fenced block hides every heading inside it from the **section** it sits in, and is where **the calendar table** lives.
_Avoid_: code block

**Section**:
One of the day's log's levelled headings and the lines under it — the notes heading and the calendar heading. A section runs from its heading to the next heading of the same or a shallower level, and a **fenced block** hides any heading inside it. Its heading is matched at its exact level and as a whole line, ignoring capitals. **A heading that carries no level is not a section** — the *tasks heading* and the *completed-tasks heading* are the two the plugin ships, and they carry none on purpose, because in a collection the level only decides whether the note counts. The distinction is what the code enforces and is not a shade of meaning: only a section can be asked for its line range in the day's log, and only a section is written into a new day. Spec issue #32 reserves a further group of them, **the day's task sections**; two of them exist, the today and overdue headings.
_Avoid_: block, region, part

**Task line**:
One Markdown checkbox line in the Obsidian Tasks emoji format, as the vault already holds it. The plugin edits one field and leaves the rest of the line byte-identical; nothing on a line is ever eaten or tidied.

**Symbol**:
The one character that sits between the brackets of a task line's checkbox. Exactly one code point, and neither `]` nor a line break, because either would stop the line reading as a task. **What may be one is the core's answer and not a feature's**: `mayBeCheckbox` in `src/core/taskLine.ts` decides, the writer asks it the same question before it puts a checkbox back, and checkbox cycling only supplies the sentence telling the person why one was refused. It is the one field on a task line a press changes; every other byte is left as written. Both names retired below are retired because they are already spent here: a **feature state** is one of seven badges and a readiness answer carries a `state` of its own, and the *marker* is the `-`, `*` or `1.` a task line keeps, or the hidden `%% task-consistency:<eid> <hash> %%` a pairing writes. *Character* is deliberately **not** retired: a symbol **is** one character, which is how the plugin's own refusals put it, so there the word is a measurement rather than a second name for this.
_Avoid_: state, marker

**Sequence**:
A named, ordered list of symbols that one pair of commands steps a checkbox through, carrying an id that survives a rename. Three parts and nothing else — an id, a name, and the symbols. **The id is never derived from the name**, because Obsidian keys a hotkey by command id, and an id built from the name would lose the person's hotkey on every rename. The two the plugin ships carry written-out ids the generator can never draw, so a shipped sequence and one the person made can never come to share one. **A sequence is not a *cycle*.** That word belongs to the act and is already spent: issue #283 names the two commands `<Sequence name>: cycle forward` and `… backward`. It is said here instead of on an `_Avoid_:` line because a retired word is swept out of every string a person is shown, and retiring *cycle* would condemn those two command names along with the misuse.

**Checkbox cycling**:
The feature, registered under the id `checkbox-cycling` and shown as *Checkbox cycling*. It gives every sequence two commands, forward and backward, each carrying that sequence's id inside its command id. **The name is the feature's and not the act's**, and the act needs no noun of its own: a **press** *steps* a checkbox one place along a sequence, both ends wrapping, and a press with nowhere to step changes nothing and says one sentence why. The feature reports itself not configured until some sequence holds two symbols **that differ**, because until then no press can move — a sequence of `x` and `x` holds two symbols and steps nowhere. The plugin's first feature, and like every other it may never reference one.
_Avoid_: toggling, checkbox states

**Date entry**:
The feature, registered under the id `date-entry` and shown as *Date entry*. A trigger character and a few typed words in Swedish or English become a date stamp on the line the person is writing in. **It writes the two kinds of date the plugin knows** — scheduled and due — **and writes both through the core**: the stamp's text and both emoji come from one export of `src/core/taskLine.ts`, and on a **task line** the date is set with the core's one-field edit, so nothing else on the line is read or changed. **The trigger is one character**, `@` unless the person changes it, and never a letter, a digit or whitespace: the popup opens on a trigger at the start of a line or after whitespace, so a letter would open one at the start of every word beginning with it. The language is this feature's own and never follows Obsidian's own interface language. The plugin's second feature, and like every other it may never reference one.

**Dismissal**:
The popup closed by the person for one trigger, with Escape or a click outside, rather than by choosing its suggestion. It silences that one trigger until a new trigger is typed, this one is deleted, or the cursor moves to a different one; choosing is not a dismissal, and a trigger the popup never opened for leaves none behind. Obsidian gives one `close()` for every kind of dismissal, so Escape and a click are not told apart. **A dismissal follows its trigger through the edits around it**: it remembers the trigger's column and the line as last read, and at each keystroke works out where the line changed, so text typed or deleted ahead of the trigger moves it, even text holding a trigger character, an edit that takes the trigger away clears it, and a trigger typed hard against it is judged fresh. Where an edit repeats what sits beside it, so the line alone cannot say where it fell, it is placed where it ends at the cursor, because a keystroke, a paste or a cut ends there; so no other trigger inherits a dismissal from an edit the person made at the cursor. **What it still cannot see**: a paste of the same character over the trigger, which holds the dismissal; two separate edits on both sides of the trigger between two keystrokes, which clear it; and an edit made away from the cursor that repeats what sits beside it, which can be placed on the wrong one of two identical stretches and pass the dismissal to the other. **A line inserted or removed above the trigger's line moves it to a new line number without touching it, which is none of decision 4's three things either**, so the dismissal follows it there — read against the couple of lines beside where it was last recorded, not the whole document, so a shift of more than one line between two readings the cursor never lands on can lose track of it, kept recorded but not applied until a later reading finds it again. **Following it across lines is bounded to a shift of one line**: landing on a line more than one away from where it was recorded never carries the dismissal there, however much its text resembles the recorded one, because a shared start is not proof of the same trigger at that distance — only within the one-line window does that coincidence stay accepted, the way the same-line limits above already are. **Whether a recorded dismissal still holds is one pure function's answer**, `recheckDismissal` in `src/features/dateEntry/dismissal.ts`, read against the line at every keystroke; the popup only keeps what it answers.

**The calendar table**:
A two-column table inside a **fenced block** whose info string reads `schema`, in the day's log, listing that day's meetings. The day view draws it; it is never the day view's own storage.
_Avoid_: schedule block, timetable

**Day view**:
The feature, registered under the id `day-view` and shown as *Day view*. Draws every `schema` fence in any note as the day's schedule — a band above a grid — reading the calendar table, the time cell and the vault layout from the core. It reaches a meeting through a click or a tap, writes a plain-text meeting into a link, and follows a rename into a `schema` fence's own links, because Obsidian does not follow one there itself. The plugin's third feature, and like every other it may never reference one.

**Grid**:
The proportional time area the day view draws, at least 08:00–16:30 and widened to fit every timed meeting, with gridlines every 30 minutes and a label on each hour. Holds blocks only; an all-day meeting never enters it.

**Block**:
One timed meeting drawn inside the grid, positioned and sized by its real start and end time, sharing width with anything it overlaps. Its text is clipped rather than the block made taller than the meeting.
_Avoid_: event

**Band**:
The strip above the grid, outside its time arithmetic, holding the bars. Left out altogether on a day with no all-day meeting, rather than drawn empty.

**Bar**:
An all-day meeting drawn in the band: one per line, full width, out of the grid's time arithmetic entirely. Looks like a block and opens the same way, but is never sized or positioned by time.

**Now-line**:
The line marking the current time, drawn only on the note the core's vault layout names as today's log, never a filename test of the day view's own. Always created on today's grid, hidden while now is outside the span, and moved once a minute by an interval that detaches on the switch.

**Bubble**:
What a block or bar shows on a hover or a tap: a block's always says its time and adds the meeting's text only where the block clips it; a bar's says the text only when clipped, and a bar whose text fits shows no bubble at all. On a phone a tap shows it and a second tap on the bubble opens the note, exactly as a click does elsewhere.

**Calendar source**:
One place the plugin reads meetings from: either an HTTPS `.ics` link it fetches, an `.ics` file inside the vault, or one calendar of a **calendar account**, picked on the settings screen since issue #1213 and read since issue #1214 (ADR 0007). `.ics` is the only calendar format the plugin knows, and a source is the only way a meeting enters it (issue #26, ADR 0001); an account's calendar arrives as the same `.ics` text inside the server's wrapper, so nothing downstream learns which kind a source is. Sources belong to the core, not to a feature, because two features read them.
_Avoid_: feed, subscription, calendar (bare — a source may hold several calendars)

**Calendar account**:
A sign-in to a calendar server that speaks CalDAV — iCloud first, any other such server too: the server's address, the user name, and an **app-specific password**. Entered once; the address and user name travel with the vault, the password stays on the device it was typed on, in Obsidian's keychain, and is typed again on each device that should read the account. Pressing *Fetch calendars* lists the calendars the account holds, and each one the person ticks becomes its own **calendar source**, with the two switches every source has; unticking it removes that source, and the plugin never adds a calendar it was not asked for. On a device with no app-specific password for the account, the account and each of its sources say *This device has no password for this account*, and nothing is asked of the server there. **Each of its calendars is read over a fixed span**, seven days back to four hundred days ahead of today, both included, and a meeting outside it is not seen, even one a repeat rule would put there. The plugin chose it and it is not a setting: it reaches past the year meeting notes looks ahead before taking a missing meeting for a cancelled one, and past the longest days-ahead window, so no setting could make an account's calendar too short for either; a setting would only add a way to break that. A refused app-specific password reads as a failed source whose message names the password, and a calendar gone from the account as one saying so; like a dead link, neither removes anything from any day. Read-only, like the links.
_Avoid_: login, credentials, subscription, iCloud account (the account is not tied to one provider)

**App-specific password**:
A password a calendar provider issues for one application, made and revoked at the provider's site, so the person's own password is never typed into the plugin. What a **calendar account** signs in with. Why it stays on the device rather than travelling with the vault, and why it is a key to more than calendars, is ADR 0007. Revoking it at the provider is the remedy if it leaks.
_Avoid_: token, API key, password (bare)

**Meeting**:
One occurrence of one calendar event on one day, read out of a source's `.ics` bytes. **`end` means two things on purpose**: for a timed meeting it is when the meeting ends, and for an all-day one it is midnight at the start of the last day the meeting is on — not the exclusive end the `.ics` file states. So `end` minus `start` is zero for a one-day all-day meeting, and a caller wanting a duration must say which kind it holds. **Carries who was invited**: `organizer`, who called it, `null` when the calendar names none, and `attendees`, everyone asked, empty when the calendar names nobody — read only because **meeting notes** needs them for a note's participants list. **Whether a meeting gets a note and a link asks `attendees` alone**: the organizer names who called it, not who was invited, so a meeting naming an organizer and nobody else does not qualify. **Carries its own occurrence key** too: stable across a reschedule, `null` for a meeting that never repeats, and a different key for every occurrence of one that does, so meeting notes can tell a moved occurrence apart from an ordinary one of the same series. **This is the one place *occurrence* is not retired**: the `_Avoid_` line below is about naming a meeting itself, never about naming which occurrence of a repeating meeting this one is — that sense is a fact about the calendar's own repeat rule, not a second name for *meeting*.
_Avoid_: event, appointment, occurrence

**The building device**:
The one device that creates the days ahead and the meeting notes. Every device may read and edit them; only this one writes them unasked. Chosen per device and never synced, so two machines cannot both create the same day.
_Avoid_: primary, master, host

**Read state**:
What one device remembers about one calendar source: when it was last read successfully, why the most recent attempt failed, **whether that failure lost some of the source's entries or all of them**, and **the address it was read from**. Per device and never synced, like the building device, because two machines read at different times. The address is what stops a re-pointed source going on claiming the last-read time the previous address earned, on the settings row as well as in the store: a read whose address is not the one the source names now is no read of this calendar, and the row says nothing has been read yet. A read state with no address recorded is taken to belong wherever the source points now. An address is compared after the same tidying the location it names receives — a file's path through the vault-path rule, a link trimmed and nothing else — so a read state earned before the loader began tidying a stored path is not disowned by that tidying alone. The grade is what the row's opening is chosen by: a source that lost only some of its entries is not called failed, because its meetings are in the day beside the row; a read state with no grade recorded is read as a total failure.
_Avoid_: cache, sync state, last fetch

**Standing problem**:
Something a feature says is wrong and that stays said: one `Notice` when it happens, and a line on the settings screen until the feature clears it again. A feature reports through a channel that already knows which feature it belongs to, so it can neither name another nor read another's. **The channel stops working when the feature stops running** — switched off, or failed to start — so nothing that is not running can speak. **What it already said is cleared by switching the feature off, and by the feature itself saying that thing is well again.** `clear` has always been on the channel; *building the days ahead* is the first feature to call it, when a day it could not read fills after all and when that day drops out of the window. **It also reports under one fixed key naming no date**: a calendar source switched on for the day that did not read whole, named, saying that no row of it is removed until it reads again — said once, standing while the source stays unread, cleared on the first run where every source reads whole. The source's own row in settings says the failure as before; this is what reaches the person who never opens settings. A feature that threw on the way up keeps its line standing on purpose: that report is the only explanation the person has for why the row reads `Failed`. **Meeting notes reports two kinds under the one channel**: one keyed by a note's own path — a collision, a refusal, or a correction not yet applied — cleared the run that next finds that path in order, and also cleared before any meeting is visited at all once that path is no longer among today's computed ones — except the path of a note the run keeps up to date where it is while a note it left as it is still exists, whose notice stands on every run until that left note is deleted; and one under a fixed key naming no single note — the address left blank the first time it matters, or the run itself failing outright — cleared once the reason for it is gone. **Task consistency reports four kinds**: a clash, keyed by the pairing's own eid, cleared once the two lines next agree; a broken pairing, keyed by the resolved path (or the link text itself when it resolves to nothing), cleared once the collection matches again; a marked line with no matching collection line at all — no breadcrumb, or a breadcrumb naming a real collection that carries no line with the same eid — keyed by its own eid either way, cleared once a line for it exists again; and a run's own failure, keyed by the collection's path or, for the whole sweep, a fixed key, cleared by the next run over the same path or sweep that succeeds. Every one of the first three is also cleared on the next run that reads the file fresh and finds the key's own line simply gone, not only on the same key resolving valid again.
_Avoid_: error, warning, notice (bare — a `Notice` is the one-off, this is what persists)

**Building the days ahead**:
The feature, registered under the id `days-ahead` and shown as *Building the days ahead*. Creates the day's log for today and each of the days ahead and fills its calendar table from your calendars, running only on **the building device** — on every other device the feature's row shows it **off**, with a sentence naming that as the reason. `standby` is the state's own name and never a word on the screen: it wears the same badge as *off* on purpose.. The plugin's fourth feature, and like every other it may never reference one.

**The window**:
**Building the days ahead**'s run of days: today through today plus `windowDays` minus one, oldest first, never a day before today. Built from today's own local date, so a run carries correctly across a month end. Whether it carries across a change of clock is **not** settled here: the suite runs in one pinned zone, and the only test naming a clock change could not have come out the other way in it.
_Avoid_: horizon, lookahead

**Row memory**:
What **building the days ahead** remembers about a row it wrote, keyed by the meeting, the date and the meeting's start minute, holding the text of the cells as the row held them after the last run and the meeting's title as it then stood, so a row can be found again after the calendar renames the meeting. **That text does not say who wrote it:** a link the person made is kept and remembered as it reads. The entry's separate `wrote` record is the one word for what the plugin itself wrote, left out when the cell was kept, and it is what *a row the plugin wrote* means — an entry stored before it existed is judged by the cell being exactly the link the plugin writes. It is also what lets a row go: a row whose meeting is no longer on its day is removed only when its remembered `wrote`, its event and its time all still match the row exactly and the row has not ended. **An entry remembers the one calendar source its meeting came from, and only that source's own whole reading can remove its row**, so a dead link on another source no longer stops this one's moves being tidied; an entry with no source — stored before this, or for a meeting two sources both hold — is removed only on a run where every source read whole. **The one ended row that goes** is a moved meeting's old row: when its own source's whole reading shows the same meeting on another day of **the window**, the row goes even though its end time has passed. For a repeating meeting that means the occurrence whose original start was on the row's day, so a cancelled occurrence of a series is still a cancellation, and an ended row whose meeting is simply gone stays. The start minute joins the key because a repeating meeting can put two meetings on one day, which the meeting and the date alone could not tell apart. A meeting the calendar moves is still found through memory, but only once its own key holds no entry at all: its row is then looked for under every other entry remembered for the meeting and the date, except one that is itself another occurrence's own current key this run, and told apart by the text each entry recorded. Each run rebuilds a meeting's entries for a date from exactly what that run wrote, so the start key a move leaves behind is dropped. Two occurrences of one repeating meeting that both move on the same day are still not told apart; that needs the calendar's own occurrence identity. Per vault, in the plugin's settings file, and nothing to do with the meeting-note half of the old plugin's ledger.
_Avoid_: ledger

**Meeting notes**:
The feature, registered under the id `meeting-notes` and shown as *Meeting notes*. Creates a note for each meeting that has at least one invited person, on a calendar source set to make one, linked from the day, running only on **the building device** — the same job as **building the days ahead**, so on every other device its row shows it **off** with the same kind of sentence, and never *not available here*. It is *not configured* until its own folder is answered; the address it leaves off every participant list is never a reason it cannot run. The field names and headings a note is written with are answered once on its card, except the **day-link field** and the **processed field**, which are the core's and answered on the core card's layout section, in English until changed, and a blank or unusable one read from the settings file is refused with a notice rather than used. What it remembers of the notes it has written — for each meeting, for each day, the note's path and who has already been offered a place on it — is kept across runs rather than rebuilt fresh like **row memory**, because a note has to be found long after its day to follow a rename; it drops a today entry whose note is gone, the day a meeting has moved away from once its rename lands, and the entry of a note it deleted. Each entry also carries what meeting notes last wrote into the note, as a fingerprint, and when the meeting ends: a note still matching it, whose meeting has not ended and is in no source's reading for the year ahead on a run where every source read whole, goes to the trash; one that differs is kept and reported once. It is keyed by the meeting's identity: the series id alone, or the series id joined to the meeting's own occurrence key for one occurrence of a repeat, so a rescheduled occurrence is found under its own key rather than confused with an ordinary occurrence of the same series. The plugin's fifth feature, and like every other it may never reference one, **building the days ahead** included.

**Join block**:
The part of an invitation's text that exists only for joining the meeting: a Skype, SAFOS or Microsoft Teams block, fenced above and below by a line of at least twenty dots or underscores and carrying that service's own wording. **Meeting notes** leaves it out of the note's agenda text, fences included, and keeps everything around it; the calendar keeps the whole invitation, so nothing is lost, and there is no setting. A boxed block without a known service's wording stays whole, even with a link in it, and a new service is one entry in `JOIN_MARKERS` in `src/features/meetingNotes/joinBlock.ts`. The Teams wording is inferred from Teams' published format and not yet seen in a real invitation.
_Avoid_: dial-in block

**Clicked note**:
The note a click on a meeting in **the day view** creates when none exists yet, on any day and any device, written filled in exactly as **meeting notes** would write it — the template, the participants, the day link — plus three more properties: `effortless-meeting`, which names the meeting, `effortless-offered`, which lists the names the click offered a place on the note, and `effortless-written`, the fingerprint of the note's body as the click wrote it. A note the run creates on the day carries `effortless-meeting` and `effortless-written` too, but not `effortless-offered`; only a clicked note carries all three. `effortless-meeting` is how **meeting notes** recognises the note as its own on the day without any record from the device that was clicked on, so it keeps the note up to date — a name invited afterward is added, a changed day or title is followed — instead of leaving it as an **adopted note**. `effortless-offered` is how a name the person deleted from the note's list by hand is known to have been offered already, so it stays removed and is not added back. `effortless-written` is how a note nobody has touched is told from one holding the person's words after the invitation's text or the template has changed since the click; when the run itself edits a note whose body still matched it — a retitled heading, an added name — it rewrites the line to the edited body in the same write, and a note whose body the person had already changed keeps its line as it was. A note the person made by hand has none of the three and is still adopted.

**Adopted note**:
A note already at the path a meeting's note would take, found with no record of it in **meeting notes**' own memory — most often one written by hand before the feature ever ran, or before its folder was even answered. At the moment it is found, it is left exactly as it is — never read, never compared and never corrected — so a note that happens to already exist there is never silently claimed and rewritten, and the meeting's participants at that moment are recorded as already on the list. From then on it is found through memory like any note this feature wrote: a name invited afterward is added, and a rename follows a changed title or day.

**Diary**:
Free writing about the day itself, in the person's own words, under its own section of the day's log — the second half of what the day's log holds, *what happened in it*. Never a form: the plugin writes no questions into it, and a person who wants prompts puts them in their own template. Days only; a meeting note's own sections are where a meeting is written about. Distinct from the notes under the notes heading, which are things to be *decided* on, and from *Review*, which is going through those notes and not writing. Any text the person wrote under the heading is a diary — one word, a dash — and the plugin never judges it; the exceptions are the diary section the day's-log template itself made, which nobody wrote, and a log for a day after today, which is never stamped. **A diary is written on its day or not at all**: an empty diary of a past day is never *waiting*, never counted and never shown in Review's list, because writing about a day in hindsight is not the routine; Review's list alone says when today's is still empty, on today's row or, once today's log is processed, on a line of its own. The plugin records the day it first saw text under the heading in **the diary-date field** of that day's log, once, so *the chain* can tell a diary written on its day from one written later (ADR 0005). A day whose log carries no diary heading simply has no diary, neither kept nor missed. Settled by the author on 2026-10-09; *diary* left the day's log's own `_Avoid_` line the same day, because the word now names this and not the log.
_Avoid_: journal, reflection, log entry

**The diary-date field**:
The property, named once for the whole vault, that the plugin fills with the date it first saw text under the day's log's diary heading. Written once and never overwritten; a value typed by hand counts. The one thing the plugin writes into an existing day's log unasked (ADR 0005, issue #1049); a log the plugin builds from the template also carries, from the moment it is built, a fingerprint of its diary section in `effortless-built-diary`, so it still reads as unwritten after the template is reworded.
_Avoid_: written field, diary timestamp

**Routine**:
Something the person means to do on its own day, and that is kept or missed on that day — never caught up later. Two exist: *the diary* written on its day, and *the review* of a day done by the next day, meaning every note of that day — its log and every note linking to it — had its processed field filled by the day after. A day that could not have the routine, with no day's log or no diary heading, is neither.
_Avoid_: habit, ritual

**The chain**:
The month grid in Review's view, Monday first, where every day carries one mark per *routine* — kept or missed, nothing for a day not yet come or one that could not have it — with arrows to earlier months and the current run of kept days beside each routine. Every day shows as it is; weekends are not skipped. Named after the *don't break the chain* method, the author's own ask on 2026-10-09. It shows and never decides, like the rest of Review. **Each day's cell is also the way to that day's log**: clicking it opens the log, creating it first through the core's note writer when it does not exist, as *Create today's log* creates today's. The click is Review's and goes with it when Review is off; there is no palette command for it. The author's own ask on 2026-10-14, replacing the Calendar plugin's one use.
_Avoid_: streak, habit tracker, calendar view

**Review**:
The feature shown as *Review*: what the person has not yet gone through of the days just past, shown as a count and a list of **waiting notes**, so that *deciding* happens even without the habit of it. It shows and never decides — a task is still filed by *Migration*, one at a time, in the note itself — and it is not a diary. **A row's open-task number counts what nothing else handles**: in a day's log only the open tasks under the notes heading, in any other note every section, and a task carrying a hidden `%% … %%` comment in neither, the section and comment rules being the core's (`sectionOfLine`, `hasBookkeepingComment`) and the same ones Migration asks. **Its view also carries *the chain***: the month of kept and missed *routines*, read from the processed field and the diary-date field, which is how a person sees whether the review and the diary actually happen on their day.
_Avoid_: reflection, inbox

**Waiting note**:
A note within the last few days whose **processed field** is present and empty. Its day is the date its name carries if it is a day's log, and otherwise the day's log its **day-link field** points to; a note with neither, or whose day has not come yet, is never waiting.
_Avoid_: unprocessed note, unreviewed note

**The processed field**:
The property, named once for the whole vault, whose empty value says a note has not been gone through yet and whose any value says it has. *Mark as processed* fills it with the day's date. **It is `layout.processedField`, answered on the core card's layout section and not on Meeting notes' card**; a vault that answered it there keeps the answer, taken from the stored Meeting notes template on load when the layout carries none.
_Avoid_: reviewed field

**The day-link field**:
The property, named once for the whole vault, that links a note other than a day's log to the day's log it belongs to; *Meeting notes* writes it on every note it makes. **It is `layout.dayLinkField`, answered on the core card's layout section**, with the same migration as the processed field.
_Avoid_: date field

**Followed task**:
A task another person has in hand, that the person follows until it lands or they let it go, whether or not they own the outcome. It is an ordinary open task whose line names the person as `@` directly followed by a link, anywhere on the line, and it stops being followed the moment its checkbox reads done or cancelled; it is never a sixth checkbox symbol (issue #1179, ADR 0006).
_Avoid_: delegated task, waiting-on task

**Recurring task**:
A task that comes back on its own rhythm — every Monday, the first of the month, three days after it was last done — because its line carries a repeat rule, written in the Tasks plugin's `🔁` form. It lives in a collection like every task, and each *round* of it is its own task: ticking the current round is what brings the next one, never the date arriving. It is never called a *routine*: a routine is kept or missed on its day and never caught up, while a recurring task rolls over (issue #1218, charting grilling 2026-10-30).
_Avoid_: repeating task, habit

**Repeat rule**:
The `🔁` text on a *recurring task*'s line that says its rhythm, in the Tasks plugin's own English wording — `🔁 every week`, `🔁 every month on the 1st`, `🔁 every 3 days when done`. The plugin reads a fixed set of these; a rule outside the set is reported once as a standing problem and the task is then treated as one that does not repeat, and a rule on a line with no date is reported the same way, because no round can be planned from it.
_Avoid_: recurrence rule, recurrence, schedule

**Round**:
One repetition of a *recurring task*: an ordinary task line with its own date, open until it is done or cancelled, after which the next round takes its place under the tasks heading and it moves under the completed-tasks heading like any finished task.
_Avoid_: occurrence (kept for meetings only), instance
